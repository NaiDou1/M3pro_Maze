## 一、结论

**本项目原本没有独立的"保险"层**，只有 6 处作用域很窄的被动保护，且全部以
「进程活着 + 传感器在线」为前提；真正的急停手段只有**物理断电**。

2026-10-03 补上三项软件保护后（见 §七），最危险的三个场景已能被软件覆盖：

```
STM32 只认最后一条 /cmd_vel，且无超时保护（AGENTS.md §3）
+ 发布依赖单线程 executor 里主线程的 spin
= 进程被强杀 / 主线程卡死时，最后的速度会一直保持
        ↓
现在：独立线程看门狗（不经过 executor）能在 0.5s 内强制归零
     但进程被 SIGKILL/OOM 时线程一并消失 —— 该场景仍需物理断电
```

## 三、五个真实的失控场景（按危险程度排序）

> **现状（2026-10-03 之后）**：场景 1~4 已由 §七 的看门狗与保鲜度门禁覆盖
> （场景 1 仅覆盖"主线程/executor 卡死"，**不覆盖 SIGKILL**）；场景 5 仍未处理。
> 下面保留原始分析，作为设计与复盘的依据。

### 场景 1：进程被强杀 → 速度锁存 → 车一直跑 ★最危险

- **机理**：`BaseDriver.set_velocity()` 只写缓存（`base_driver.py:120-127`），上线靠 20Hz 定时器
  （`:97`），而定时器要主线程 `spin` 才会触发。STM32 无超时保护，会一直按最后一条指令走。
- **触发**：`kill -9`、OOM killer、**关闭终端窗口（SIGHUP）**、launch 强制清理。
  这些情况下 `finally` 不执行 → 归零指令永不发出。
- **后果**：车以最后的速度（前进 0.15m/s，或带转向分量）持续运动。
  若正好卡在走格循环的 2.5s 窗口内，就是**无限前进直到撞墙**，且此时软件保护全部失效。
- **唯一出路**：物理断电。
- **缓解现状：零。**

### 场景 2：主线程阻塞 → 定时器停发 → 同样锁存

- `wait_until_ready()` 用 `time.sleep()` 阻塞且**不 spin**（`arm_controller.py:156,158`），
  抓取期间连续 2s 不 spin 属正常行为。此时若最后一条指令非零，车会继续走。
- 目前靠"进抓取前必先 `stop()`"这一**约定**保证，属约定而非机制。
- 更极端：若主线程因 IK 服务异常而长期卡住，20Hz 心跳一并消失。

### 场景 3：激光失效 = 碰撞保护与开口判定同时归零，且无法察觉

```python
sensors.sector_min_range() → 无有效点返回 None          # sensors.py:145-147
is_path_clear()  → d is None or d > threshold → True     # sensors.py:155  None 当"通畅"
is_front_blocked() → d is not None and d < safety → False # motion_controller.py:154  None 当"不阻塞"
```

- 雷达挂了、被遮挡（透明/吸光表面）、**或数据陈旧**（无任何 `scan_age()` 检查，只有 `get_scan()` 返回最后一条），
  三处判断都会退化成"前方一路通畅"。车会继续以 0.15m/s 前进，并把墙当作开口。
- 里程计失联至少还有一条告警（`base_driver.py:191`），激光连告警都没有。

### 场景 4：相机失效 → 静默直行，不循迹

- `_latest_image()` 返回 `None` → `steering` 保持 0（`motion_controller.py:212-216`）→ 不做任何循迹，
  仅靠里程计走完 0.37m；同时不检测方块、不触发丢线保护（`detect()` 根本没被调用）。
- `sensors.rgbd_age()` 已经写好，但**全仓零调用**——保鲜度检查形同虚设。

### 场景 5：转向、后退、对位过程中的保护空白

| 场景 | 现状 | 风险 |
|---|---|---|
| `turn_to_heading` 原地转 90°/180° | 全程只看 yaw，无激光守卫 | 180° 掉头几何余量仅约 2.5cm/侧（AGENTS §5.11），PLAN 承诺的"<8cm 立即停"未实现 |
| 后退（`advance(负值)`、`_emergency_backoff`） | 无后方检测，盲退最多 0.2m | 倒车撞墙/撞已收集的方块 |
| 对位（目标 0.20m） | 落在碰撞阈值 0.25m **之内** | 雷达若扫到方块 → 误判碰撞 → 白白后退 0.2m，甚至永远进不了包络 |
| 侧向 | 前扇区仅 ±15°，车体侧向 9.25cm 余量不在视野内 | 横向漂移蹭墙不会被保护捕获（只会刮伤，通常不致损毁） |

## 四、机械臂：全开环，无任何"保险"

- **无位置反馈**（AGENTS §3 已确认）：到位判据只有 `arm6_joints.time` 计时 + 事后视觉复查。
- **无力矩/电流限制**：撞墙或自碰撞时舵机会**堵转到指令结束**（单步最长 2s），持续堵转会发热。
- **无姿态禁区**：`send_joints` 只校验关节数=6；角度裁剪仅在 `grasp_fsm._sanitize()` 里做
  （joint4>90 截断、joint6 由逻辑覆盖），joint1/2/3/5 仅 0~180 钳位。
- **标定模式更危险**：`maze_calib line_pose` 允许键盘把任意关节 ±5°/±15° 推到任意角度，
  **没有禁区、没有碰撞检查**，可能把臂顶进车体或桌面。
- **断电掉落**：舵机断电失去保持力矩，机械臂会因重力下落；携方块时尤其注意。

## 五、上机前检查清单（照做可规避绝大多数损坏）

> **一键脚本**：[`scripts/maze_test.sh`](scripts/maze_test.sh) 把本节"第一次运行"的前四步自动化了：

> `--run` 才驱动底盘，且要打字确认 `RUN`。首次仍建议人工逐条核对下面每一项。

**第一次运行（必须）**

- [ ] 车放在**空旷地面**（≥1.5m×1.5m），**不要直接放进迷宫**

- [ ] `ros2 topic hz /scan`、`/camera/color/image_raw`、`/odom_raw` 确认在出数据（**不是"有话题"而是"有频率"**）
- [ ] 轮子**架空**（垫起）跑第一次，观察 `/cmd_vel` 与机械臂动作，确认方向、量级正确
- [ ] 手放在**电源开关上**，全程有人守着

**每次运行**

- [ ] 启动日志里确认出现 **`速度看门狗已启用：非零指令超过 0.50s 未刷新即强制归零`**；若看到"看门狗被禁用"的 WARN，立即停手检查 `cmd_watchdog_timeout`
- [ ] 只按 **Ctrl-C** 退出，**不要 `kill -9`**，不要直接关终端窗口（会发 SIGHUP）
- [ ] 退出后确认终端打印了退出日志（`任务完成/任务中断`），否则立即断电
- [ ] 运行中若发现雷达/相机掉线（`ros2 topic hz` 掉到 0）：软件会在 0.5s（激光）/2s（相机）内自动停车并记 WARN，但**仍建议立即断电**——自动保护不等于无人值守
- [ ] 若相机日志出现 `onDeviceDisconnected`：说明 USB 掉线重连（实测 USB2.0 下启动约 27s 后发生一次，约 7s 恢复），**自检会误报相机 FAIL**，等 10s 重试即可；根治要换 USB3.0 口/直连不 Hub
- [ ] `maze_calib motion` 只在空地跑：它按固定 3s/8s 开机，**无任何碰撞保护**，8s×0.5rad/s ≈ 229° 足以顶墙堵转
- [ ] `maze_calib line_pose` 时手别离开 Ctrl-C，臂没有禁区

**绝对不要**

- ❌ 车在桌面上直接跑 `maze_run`（自检通过后**立即开始运动**，没有二次确认）
- ❌ 在窄通道里跑 `maze_calib motion`
- ❌ 无人看守时跑抓取流程
- ❌ 用 `pkill -9` / 关闭终端来停止任务

## 七、已落地的保护（2026-10-03 实现并验证）

代码提交：`cbfc56a feat(safety): 速度看门狗与激光/相机失效保护`、
`69801fb test(safety): 看门狗判定与保鲜度门禁单测`。

### 7.1 速度看门狗（`base_driver.py:46` `CommandWatchdog`）

```
set_velocity(非零)  ──feed──►  看门狗记录时刻
每 20ms 控制周期刷新一次           │
                                 ├─ 0.5s 内被刷新 → 正常
                                 └─ 超时未刷新 → 回调 _force_zero：
                                    缓存清零 + 立即 publish(0,0,0) + WARN
```

- 跑在**独立线程**，只依赖 DDS 发布，**不经过 executor**——这是它能覆盖
  "主线程阻塞 / executor 卡死"的原因；20Hz 定时器做不到这一点。
- 语义很自然：**非零指令必须被持续刷新**，`stop()` 本身也是刷新（零速永远安全）。
- 阈值 `cmd_watchdog_timeout: 0.5`（s），现场可用 `0` 关闭（不建议）。
- 触发次数经 `BaseDriver.watchdog_trips` 可查，便于自检与复盘。

### 7.2 激光 / 相机保鲜度门禁

| 位置 | 行为 |
|---|---|
| `SensorHub.scan_age()` | 补上激光保鲜度（原先只有 `rgbd_age` 且零调用） |
| `MotionController.sensors_ok(need_vision)` | 激光年龄 > `scan_timeout`（0.5s）→ 失效；`need_vision` 时相机年龄 > `vision_timeout`（2.0s）→ 失效 |
| `advance()` | **动作前 + 每个控制周期**各查一次；前进要求激光+相机，后退只要求激光；失效即停车返回 False |
| `turn_to_heading()` / `strafe()` | 动作前查激光；失效则不启动（避免把车停在半路） |
| `mission_manager._run_explore()` | 勘测路口前等待激光恢复 `sensor_wait_timeout`（3s）；仍失效 → FAULT（**防止把"失效"写成拓扑里的假开口**） |

为什么必须硬失败：激光失效时 `sector_min_range` 返回 `None`，而 `is_path_clear`
与碰撞保护都把 `None` 当"通畅"；相机失效时循迹偏差恒 0，车会闷头直行。
两者都会让"保护"退化成"放任"。

### 7.3 验收（2026-10-03 实测）

| 项 | 结果 |
|---|---|
| `pytest test -q` | **91 passed**（原 75 + 新增 16） |
| `colcon build --packages-select maze_explorer` | 通过 |
| `ros2 run maze_explorer maze_run --check-only` | 正常输出四项自检 |
| 改动文件 `ament_flake8` | 无违规 |
| **看门狗端到端**（executor 完全不 spin，模拟主线程卡死） | **通过**：订阅者 t=0.001s 收到 `(0.15, 0, 0.10)`，t=0.318s 收到 `(0, 0, 0)`；`watchdog_trips=1` |

端到端验证方法（脚本已执行，非推断）：起 `BaseDriver(watchdog_timeout=0.3)` 与一个订阅
`/cmd_vel` 的监听节点，**监听节点在后台线程 spin，发布节点的 executor 永不 spin**；
手动 `publish_now()` 把非零指令发出去（模拟下位机已锁存），然后主线程只 `sleep`。
实测输出：

```
t=0.001s  linear.x= 0.150  angular.z= 0.100   ← 非零指令已上线
t=0.318s  linear.x= 0.000  angular.z= 0.000   ← 看门狗独立线程归零
[WARN] 看门狗触发：0.30s 未收到新的速度指令，已强制归零（累计 1 次）
```

这条链路正是 20Hz 定时器做不到的：定时器同样跑在 executor 上，主线程卡死时它一并停摆。

### 7.4 仍未覆盖的场景（务必记住）

| 场景 | 为什么没覆盖 | 兜底手段 |
|---|---|---|
| `kill -9` / OOM / SIGHUP | 看门狗线程随进程一起消失 | **物理断电** |
| 舵机堵转、机械臂撞墙 | 硬件无反馈，软件无从判断 | 运行前清空臂活动范围 |
| 手柄接管 / 人肉急停 | 未实现，且手柄自启被主动关掉 | 物理断电 |
| 全局超时 | 截止看门狗未实现 | 人工盯表 + Ctrl-C |
